# 設計判断記録 (ADR)

設計判断、採用理由、変更履歴を記録する。新しいエントリは末尾に追加する（古い順）。

## 記録フォーマット

```
## D-XXX: タイトル

- 日付: YYYY-MM-DD
- 状態: 採用 / 却下 / 廃止（廃止の場合は後継のDを記載）

### 背景
- なぜこの判断が必要になったか

### 決定
- 何を決定したか

### 理由
- なぜその選択をしたか（検討した代替案があれば併記）

### 影響
- この決定が及ぼす影響、制約
```

## D-001: 技術スタックはWeb技術（React + TypeScript + Vite）+ Capacitorを採用する

- 日付: 2026-08-06
- 状態: 採用

### 背景
- 「どこでもプレゼン」はAndroid APK配布を最終目標としつつ、開発中はPWA/Web版でよいという要件があった。開発コンテナにはNode.js（node22）・JDK 21・Gradle 8.14.3はあるが、Android SDK・Flutter SDK・エミュレータ/実機は存在しない。

### 決定
- React + TypeScript + Viteでフロントエンドを実装し、Phase 4でCapacitorを導入してAndroid APK化する。状態管理ライブラリ・ルーターは追加せず、`useReducer`とHistory APIで画面遷移を実装する。CSSは素のCSS＋カスタムプロパティ（デザイントークン）とし、Tailwind等は導入しない。

### 理由
- Flutterは却下: SDK未導入で導入コストが大きく、「開発中はPWA/Web版でよい」という要件とも合わない。自動レイアウトエンジンの本質はテキスト計測と矩形配置の純粋計算であり、DOM/Canvasを持つWebの方が実装・検証コストが低い。
- Capacitorは採用: 開発したWebビルド成果物をそのままAndroid WebViewに載せられ、Phase 1〜3を純Webとして進め、Phase 4で`npx cap add android`するだけでAPK化できる。導入済みのJDK 21/Gradle 8.14.3がCapacitor 8のAndroid要件と一致する。
- 状態管理ライブラリ・ルーターは画面数（3画面）と単一ドキュメント編集という要件規模に対して過剰な抽象化になるため見送った（判定ラダー1: そもそも必要か）。

### 影響
- `npm install`はNode 22系（`/opt/node22`）を使う必要がある（Vite 8のengines要件）。
- Phase 4でAndroid SDKの追加導入が必要。実機・エミュレータがこの開発コンテナにないため、debug APKのビルド成功とビルド手順書の整備をPhase 4の完了条件とし、実機での動作確認はUser側で行う。

## D-002: 自動レイアウトエンジンをレンダラ非依存の純粋関数として設計する

- 日付: 2026-08-06
- 状態: 採用

### 背景
- 自動レイアウトは本アプリ最大の特徴機能であり、編集画面のライブプレビュー・プレゼン画面・PNG/PDF出力の3箇所で同じ結果を再現する必要がある。

### 決定
- `layoutSlide(slide, measurer): LayoutResult`という純粋関数を`src/layout/`に実装する。入力テキストの解析（`parse.ts`）→重要度付与（`analyze.ts`）→テンプレート選択（`templates.ts`）→文字計測・配置（`measure.ts`/`layout.ts`）の順に処理し、出力は1280×720の仮想座標系における絶対配置ボックス列（`LayoutResult`）とする。DOM/Canvas双方のレンダラはこの同じ`LayoutResult`を描画するだけとし、レイアウト判断ロジックを二重実装しない。
- AI補助機能（タイトル推定・優先順位判定・レイアウト最適化・文字量警告・文章要約・読みやすさ評価）は、オフラインファースト要件を優先し、外部LLM APIを呼ばずルールベース/ローカル処理（キーワード辞書・文字数・行数等の統計）で実装する。

### 理由
- レンダラ非依存にすることで、`html2canvas`系ライブラリ（日本語フォント埋め込みで壊れやすい）が不要になり、PNG/PDF出力とプレビューの見た目のズレを構造的に防げる。文字計測を`TextMeasurer`インタフェースで注入することで、エンジン自体をDOMなしでユニットテストできる。
- 外部LLM API連携は将来`analyze`の結果を差し替える形で拡張できる余地を残すが、今回はインタフェースを先回りして作らない（YAGNI）。

### 影響
- 新規スライドテンプレート（2カラム・画像レイアウト等）の追加は`templates.ts`の変更のみで完結する。
- Phase 2のCanvasレンダラ・PDF出力は`LayoutResult`をそのまま消費するだけで、レイアウト判断の再実装は発生しない。

## D-003: エディタ・プレゼンモード改善（ダークモード/没入型プレゼン/複製削除/自動整列）の設計方針

- 日付: 2026-08-07
- 状態: 採用

### 背景
- 「編集性・視認性・プレゼン時の没入感を向上させる」というIssueに対し、(1)ダークモード、(2)プレゼンモードの没入表示、(3)Editor画面からのスライド複製・削除、(4)自動レイアウトへの整列軸追加、の4機能を実装する。plannerが調査・設計した。

### 決定
- **ダークモード**: CSS変数2セット化＋`document.documentElement.dataset.theme`切替。`localStorage`（キー`dokopre.theme`）に`'system'|'light'|'dark'`を永続化、初期値は`'system'`（`prefers-color-scheme`追従）。切替UIはHomeScreenヘッダーの循環トグルボタン1つのみ（設定画面は新設しない）。**スライド面（`--slide-bg`/`--slide-fg`/`--slide-muted`）はテーマから独立した固定トークンとし、`canvasRenderer.ts`のハードコード色と一致させる**（PNG/PDF出力とプレビューの見た目を常に一致させ、D-002の「プレビューと出力の構造的一致」を維持するため）。Androidネイティブ時は`@capacitor/core`同梱の`SystemBars.setStyle()`でステータスバー配色も追従させる（新規パッケージ追加なし）。将来のテーマ追加は「`:root[data-theme='xxx']`ブロックを1つ足す」「`ThemeId`ユニオンに1値足す」の2箇所で完結する構造とし、テーマプラグイン機構等は作らない。
- **没入型プレゼン**: Android（Capacitorネイティブ）では`SystemBars.hide()/show()`、Web/PWAでは`Element.requestFullscreen()`/`document.exitFullscreen()`と環境で明確に分岐する（Capacitor 8のWebView実装では`requestFullscreen()`が実効を持たないため、両方を試す実装はしない）。`requestFullscreen()`はユーザー操作起因が必要なため、EditorScreenの「▶ 発表」ボタンの`onClick`内（Web時のみ）で呼んでから画面遷移する。失敗時は通常表示のまま継続（既存のtry/catchパターンを踏襲）。
- **スライド複製・削除**: 既存の要約Undo（`summarizeUndo`、単一スロット・直前1回のみ・他操作で失効）を判別共用体`EditorUndo`に拡張し、削除のUndoに流用する（新しいUndoの仕組みを乱立させない）。複製は非破壊操作のためUndoを付けず、実行時に既存Undoをクリアする。複製時は`Block.id`を含めすべて新規採番する（IDの衝突を避けるため）。UIはEditorScreenツールバーに「スライド」ボタンを1つ追加し、既存のボトムシートパターン（HomeScreenのデッキ操作シートと同型）で複製・削除を提示する。
- **自動整列**: `LayoutBox.align`（既存の`'left'|'center'|'right'`）はレンダラ含め変更しない。新設する`AlignId = 'left'|'center'|'centerBox'|'right'`を`LayoutResult.align`に持たせ、判定は`templates.ts`の`selectAlign(analyzed, template)`（判定ラダー形式、外部API不使用）で行う。「左右中央揃え」＝ボックス自体を内容幅に縮めて枠内で水平中央に配置（`centerBox`）、「中央揃え」＝テキストを枠幅いっぱいのまま`text-align: center`、という解釈を採用する。**右揃え（`right`）は型・実装として用意するが自動選択の対象にはしない**（Userに確認済み。画像が常に右固定で配置される既存テンプレート構成では、テキストを右揃えにする合理的な入力パターンが存在しないため）。

### 理由
- 状態管理ライブラリ・設定画面を新設しない（D-001の「画面数を増やさない・過剰な抽象化をしない」方針を維持）。
- スライド面をテーマから独立させないと、ダークモード時にプレビューだけ暗くなりPNG/PDF出力（常にライト固定）と食い違う。これはD-002が保証する構造的一致を壊すため、最重要の設計判断として固定トークン化を採用した。
- 右揃えの自動選択は、判断根拠のない機能を追加するとかえって可読性を下げるリスクがあるため、AGENTS.mdの「そもそも必要か」の判定に照らし見送った。将来「画像を左・テキストを右」の鏡像テンプレートを追加する場合に再検討する。

### 影響
- フェーズ4（自動整列）の適用により、既存デッキの一部スライドで`bullets`/`statement`テンプレートの配置が変わりうる（データそのものは変更されない）。
- ダークモード導入後も、PNG/PDF出力の見た目はダーク/ライトどちらの設定でも変化しない（レビューの完了条件に含める）。
- 実装はダークモード→複製・削除→没入プレゼン→自動整列の順にフェーズ分割し、各フェーズごとにDeveloper→Reviewerサイクルを回す。
